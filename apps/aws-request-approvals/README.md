# AWS — Request and Approval API

All demonstration data is synthetic. Portfolio project, not an employer integration. **Cloud deployment: VERIFIED on 24 October 2026; demo resources subsequently removed.**

The approved eu-north-1 stack reached CREATE_COMPLETE. Fifteen real HTTP calls verified intake, approval, idempotency, conflicts, unsigned denial and signed reader-only mutation denial. Direct DynamoDB reads verified the approved version, two audit events and two receipts. Regional CloudWatch logs and seven-day retention passed. Independent checks confirmed all dedicated resources were deleted. [Redacted evidence](../../docs/evidence/aws-cloud-verification.json) includes timestamps, source/bundle hashes, responses and cleanup checks. This was a temporary synthetic demo with one owner principal, not a production service or independent human approval workflow.

The Operations analyst submits a complete request; an Approver records a reasoned decision. The service rejects malformed input, missing/wrong-role identity, stale versions and reused keys with a different body. A DynamoDB transaction writes the request, audit event and idempotency receipt. Reads are strongly consistent; event history is bounded to 50 recent entries.

Local: set distinct random 24+ character LOCAL_API_TOKEN and LOCAL_APPROVER_TOKEN values in your shell and run `pnpm aws:local`. The first maps to a synthetic requester/reader, the second to an approver/reader. The server binds 127.0.0.1:3101 and uses in-memory persistence. Send Authorization: Bearer <appropriate local token>; mutating requests also require Idempotency-Key. `pnpm test:http` generates temporary credentials and verifies the two-identity flow without printing tokens. The [OpenAPI](openapi.yaml) is the HTTP contract; [tests](tests/api.test.ts) demonstrate acceptance and failure behaviour. It is not an IAM emulator.

Local principal/provenance hardening rejects the exact submitting principal's own approval/rejection, including dual-role identities. Missing or ambiguous server-written submission provenance fails closed. Lost-acknowledgement tests prove an unchanged retry recovers a committed local result once; 503 can mean an uncertain write, not necessarily no write. These changes postdate the verified cloud source and have **not been deployed to AWS**. Different session IDs may belong to one human; independent human separation remains unverified. [Readiness backlog/playbook](../../docs/AWS-PRODUCTION-READINESS.md), [current evidence](../../docs/evidence/phase4-verification.json).

DynamoDB Local integration: `docker compose up -d dynamodb`, then run `pnpm test:integration` (also requires Azurite). This creates and deletes a uniquely named local table only; credentials are the emulator's dummy values. Do not point the test at real AWS.

## Manual deployment runbook (fresh approval required for another run)

1. Install AWS/SAM tooling through the provider's documented installer; authenticate with a profile outside chat. For the new GitHub sign-in project experience, use the supported `aws login --profile serviceflow` browser flow after local-access approval; never paste credentials into chat. Owner completes the browser grant. Inspect Billing and complete [COST_GATE](../../docs/COST_GATE.md).
2. Run all local checks. Run `pnpm build`; dist/lambda.js includes SDK dependencies, and dist/package.json explicitly selects CommonJS for the SAM handler.
3. Run `sam validate --lint --template-file apps/aws-request-approvals/template.yaml` and `sam build --template-file apps/aws-request-approvals/template.yaml` after `pnpm build`. Both passed with workspace-local SAM 1.170.0. SkipBuild metadata deliberately packages the already-built Lambda bundle; this does not invoke Lambda or deploy AWS resources.
4. Review transformed IAM, resource list, region, runtime, packaging and account quotas. Confirmed project region is eu-north-1. New-project managed defaults can grant broader runtime access than the explicit role policy; verify effective permissions and regional CloudWatch Logs compatibility. Concurrency 1 can be unavailable in some account configurations; inspect before deployment, do not silently remove the limit.
5. Obtain explicit owner approval before `sam deploy --guided`. Use a dedicated stack/serviceflow project tag. Do not upgrade a Free plan to Paid to bypass service restrictions.
6. Pass exact API Gateway-reported principal ARNs into requester/approver/reader parameters; no wildcard allowlists. Assumed-role session ARNs differ from IAM role ARNs: inspect redacted request context during a controlled call and deliberately configure the right principal representation. Grant callers only execute-api:Invoke on intended routes. Role checks fail closed for unlisted principals.
7. Use a SigV4 client with the local credential provider chain (never copy keys into code/chat). A new verification run must use deliberately reviewed distinct requester/approver identities; the earlier one-owner run cannot verify the new control. Submit, deny a dual-role submitter's own decision, reread unchanged state, decide with the authorised independent principal, replay, test stale version, and attempt the POST unsigned. Unsigned must return 401/403 and no side effects. Save redacted outputs and audit evidence. Review stable human identity mapping before any production claim.
8. Inspect CloudWatch retention, request counts, DynamoDB capacity/storage and Billing. Run `sam delete --stack-name <dedicated-stack> --region <approved-region>` after evidence capture, including stack-managed table/log resources. Check/delete the deployment S3 artefacts/bucket if dedicated and no longer needed. Recheck delayed billing.

The verified temporary endpoint was removed after evidence capture; no continuously hosted service is claimed. The explicit transaction policy uses item-level dynamodb:PutItem on this table and no table scan. AWS's managed project defaults can grant broader effective access; the narrow template policy alone does not prove least privilege.

## Local operations and failure exercise

The shared execution wrapper emits one bounded completion metric with operation/status/outcome/duration and a server-context correlation ID, also returned as x-correlation-id. It does not log bodies, tokens, identities, raw paths, request/customer values, keys or SDK diagnostics. Caller correlation/principal headers are ignored. A failing log sink cannot change a committed result. This covers handler calls only, not gateway/runtime rejections; process liveness is not persistence readiness.

`pnpm aws:resilience` runs a bounded memory exercise; `pnpm aws:resilience dynamodb-local` uses only the fixed loopback emulator and creates/deletes its own temporary table. Both record 76 service invocations for repeated failures, recovery, uncertain commit and 16-way races/replays. Cancellation containing capacity/contention/unknown reasons stays 503, while conditional-only cancellation is 409. [Observed local evidence and operational playbook](../../docs/AWS-LOCAL-OPERATIONS.md). No accepted production latency/load target, actual AWS fault, SDK backoff timing or alarm delivery is claimed.

## Local release and identifier preparation

Intake without a requestId now generates `REQ-<lowercase UUID v4>`; explicit valid four-digit references remain supported. Clients must treat IDs as opaque strings. `pnpm build`, `pnpm aws:artifact prepare` and `pnpm aws:release-test` prepare/inspect the actual bundle and rehearse local promotion/rollback without any AWS call. This has not been cloud deployed. [Runbook, checksum trust and schema rollback limits](../../docs/AWS-LOCAL-RELEASE-AND-IDENTIFIERS.md).
